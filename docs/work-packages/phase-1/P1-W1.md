# P1-W1 — Build the Control Plane service shell

## 1. Purpose

Turn the Go Control Plane placeholder into the durable modular-monolith
foundation required by every other Phase 1 Control Plane package.

## 2. Why now

Authentication, environments, enrollment, health, audit, and jobs need shared
startup, configuration, transaction, migration, and module boundaries.

## 3. Inputs and decisions

- Go modular monolith using `net/http` and minimal middleware.
- PostgreSQL 18.x with explicit SQL and generated typed access.
- `pgx/v5`, `sqlc`, and `goose`, pinned to secure supported versions.
- OpenTelemetry-first instrumentation with no mandatory vendor backend.
- Development-only forward migration and reset/reseed recovery policy.

## 4. Dependencies

P1-G0 and Product Owner approval of the Phase 0 gate.

## 5. Scope

- Configuration and lifecycle for one Control Plane process.
- Module shells for auth, environment, devices, deception placeholder, health,
  audit, jobs/outbox, and API.
- PostgreSQL connection management, migrations, typed queries, and explicit
  transaction boundaries.
- Readiness/liveness endpoints and structured startup/shutdown behavior.
- Append-oriented audit substrate; P1-W10 owns the complete audit model.

## 6. Non-goals

- User login, environment behavior, enrollment, or device streaming.
- A second database, broker, cache, ORM, or microservice split.
- Production deployment sizing or high availability.

## 7. Allowed paths

Only the paths listed in frontmatter. Workflow changes are limited to the
approved PostgreSQL integration gate.

## 8. Security constraints

No credentials in source or logs. Database URLs and master material enter via
approved configuration boundaries. Health endpoints expose no secrets or raw
internal errors.

## 9. Implementation requirements

- Human-readable SQL migrations embedded or packaged reproducibly.
- No ORM auto-migration and no down migrations.
- Rollback documentation must say to revert code and reset/reseed the
  development database; do not add compatibility shims.
- Module code cannot directly reach another module's tables.
- Service restart must preserve committed state.

## 10. Required tests

- Unit tests for configuration, lifecycle, and transaction behavior.
- PostgreSQL 18 integration test from an empty database.
- Migration idempotency/version tests and deliberate migration failure test.
- Restart persistence test.
- `task validate` and container smoke build.

## 11. Acceptance criteria

- A fresh PostgreSQL database migrates successfully.
- The documented development reset/reseed strategy is reproducible.
- Restart preserves committed state and unfinished durable job metadata.
- Module boundaries and startup failure states are explicit.

## 12. Evidence required

Migration output, PostgreSQL integration logs, restart result, dependency and
license inventory, and CI links.

## 13. Stop and escalate

Stop for a new datastore/broker/runtime, ORM auto-migration, cross-module table
access, production secret, or any requirement for backward compatibility.

## 14. Deliverables

Control Plane foundation, migrations, generated query layer, integration tests,
runbook, and acceptance evidence.
