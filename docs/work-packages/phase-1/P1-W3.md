# P1-W3 — Implement the environment domain

## 1. Purpose

Create the single-organization environment and private IPv4 zone model used by
enrollment, desired state, health, and later deception placement.

## 2. Why now

Devices and desired state require stable environment ownership and validated
network-zone identities before they can be connected safely.

## 3. Inputs and decisions

- One organization singleton with multiple environments.
- Environment create/read/update; deletion is not part of Phase 1.
- RFC1918/private IPv4 zones using canonical CIDR representation.
- Any overlap inside the same environment is rejected in Phase 1.
- Saving configuration never performs an active network scan.

## 4. Dependencies

P1-W1 module/database foundation and P1-W10 audit append API.

## 4.1 Product Owner implementation contract — 2026-08-28

The Product Owner approved `W3-C1-A` through `W3-C7-A` as one binding
implementation package:

- **W3-C1-A — narrow runtime/evidence allowlist expansion:** add only the
  Control Plane app composition path, root Taskfile, and exact P1-W3 security
  review path. Those additions are restricted to P1-W3 runtime wiring,
  integration-fixture registration, and security evidence. Auth-domain,
  audit-vocabulary, Edge, Web Console, Protobuf, workflow, repository-setting,
  secret, and dependency-manifest changes remain unauthorized.
- **W3-C2-A — singleton organization and identity:** migration creates exactly
  one immutable organization with a PostgreSQL 18 UUIDv7 identity. Phase 1 has
  no organization create/delete/selector API. Every local owner session belongs
  implicitly to the singleton; every environment references it. Environment
  and zone IDs are UUIDv7. Display names are trimmed, NFC-normalized, bounded to
  1–128 code points and 512 UTF-8 bytes, and unique by normalized Unicode
  case-fold within their parent scope. Descriptions and tags are absent.
- **W3-C3-A — environment REST, status, and concurrency:** expose authenticated,
  bounded organization and environment read/create/update operations. There is
  no environment deletion. Responses carry identity, display name, revision,
  zone count, timestamps, and exactly `needs_zones` or `zones_defined`
  configuration status; these values never imply health or protection.
  Updates require a strong `If-Match` revision ETag. Missing and stale
  preconditions return `428` and `412` respectively without mutation or audit.
- **W3-C4-A — zone/CIDR contract:** expose authenticated, bounded zone
  create/read/update/remove operations. Inputs must already be canonical IPv4
  network prefixes wholly contained by RFC1918 `10/8`, `172.16/12`, or
  `192.168/16`. Reject malformed, host-bit, public, unspecified, loopback,
  link-local, multicast, IPv6, zero-prefix, duplicate, nested, and overlapping
  prefixes in one environment. PostgreSQL uses `cidr`; overlap across different
  environments remains allowed. Zone update/remove requires `If-Match`.
- **W3-C5-A — durable concurrency and device integrity:** migration `00005`
  stores the singleton, environments, and zones through explicit SQL/sqlc.
  Transaction-scoped per-environment serialization plus uniqueness/overlap
  queries gives concurrent zone mutations one deterministic winner. Add a
  restrictive device-to-environment foreign key and update every in-repository
  enrollment consumer atomically. Development databases with orphan device rows
  use the approved reset/reseed recovery path; no compatibility layer is added.
- **W3-C6-A — authorization, bounds, and atomic audit:** reads require a valid
  P1-W2 session; mutations additionally require exact HTTPS Origin and CSRF.
  The API exposes no caller-selectable organization context and scopes every
  lookup to the singleton. Strict JSON uses a 16 KiB body cap; collection limits
  default to 50 and cap at 200; database details stay private and responses are
  no-store. Environment/zone mutations append the approved P1-W10 actions with
  bounded redacted before/after snapshots in the same PostgreSQL transaction.
- **W3-C7-A — acceptance and no-scan evidence:** authoritative PostgreSQL 18
  plus HTTPS evidence uses real P1-W2 session/CSRF/Origin authorization and
  covers CIDR boundaries, overlap, concurrency, rollback, device referential
  integrity, restart, ETags, bounds, redaction, and forbidden methods. Saving
  only performs PostgreSQL work; discovery, probing, routing, firewall mutation,
  and P1-W9 health remain outside P1-W3.

## 5. Scope

- Organization singleton initialization.
- Environment create/read/update and status projection.
- Zone/CIDR create/read/update/remove within an environment.
- Canonical CIDR, duplicate, overlap, and input validation.
- Before/after audit references for all mutations.

## 6. Non-goals

- Multi-tenancy, arbitrary public networks, IPv6, VLAN automation, active
  discovery, IP allocation, decoy placement, or environment deletion.

## 7. Allowed paths

Only the environment domain, its API/storage adapters, tests, and runbook paths
listed in frontmatter.

## 8. Security constraints

Reject malformed, public, loopback, link-local, multicast, zero-prefix, and
overlapping CIDRs. Authorization must scope every mutation to the authenticated
organization context.

## 9. Implementation requirements

- Use Go `net/netip`-class canonical parsing and containment checks.
- Enforce overlap and uniqueness in both domain validation and transactional
  persistence where possible.
- Store normalized prefix/network values, not user formatting.
- Return actionable validation errors without leaking database details.

## 10. Required tests

- At least two valid RFC1918 zones in one environment.
- Duplicate, nested, partial-overlap, public, malformed, and boundary CIDRs.
- Concurrent update conflict and transaction rollback.
- Save-without-scan assertion and complete audit history.

## 11. Acceptance criteria

- AC-ON-003 passes with at least two private IPv4 zones.
- Dangerous/ambiguous overlapping configuration is rejected deterministically.
- Save causes no probe, scan, route, address, or firewall mutation.
- Owner-visible status and audit history survive restart.

## 12. Evidence required

API examples, validation matrix, PostgreSQL integration results, audit samples,
and CI links.

## 13. Stop and escalate

Stop for IPv6 or public-network scope, nested-zone precedence, active discovery,
automatic network changes, or a schema that introduces multi-tenancy behavior.

## 14. Deliverables

Environment module, OpenAPI contract, migrations/queries, validation tests, and
operator documentation.

## 15. Implementation evidence — 2026-08-28

- Domain/application: immutable singleton projection; normalized bounded names;
  canonical RFC1918 validation; environment/zone services; revision handling.
- Persistence: migration `00005`, explicit sqlc queries, per-environment
  transaction advisory locking, overlap detection, device foreign key, atomic
  P1-W10 audit snapshots, and restart durability.
- HTTP: TLS-only authenticated reads; exact Origin and CSRF mutations; strict
  16 KiB JSON; bounded lists; strong ETags; sanitized no-store responses; no
  organization selector or environment deletion.
- Contract/operations: `openapi/guardian.yaml`, environment development
  runbook, and `security/p1-w3-environment-review.md`.
- Focused evidence: `task environment:integration` runs PostgreSQL 18 and real
  P1-W2 HTTPS authorization across CIDR boundaries, overlap/concurrency,
  rollback, device integrity, restart, ETags, bounds, redaction, forbidden
  methods, and the no-scan assertion.

Product Owner application/security acceptance remains open until the PR is
green, the evidence report is posted, and the owner explicitly accepts it.
