# P1-W9 — Implement the platform health model

## 1. Purpose

Expose truthful, actionable health conditions from Edge runtime facts through
the Control Plane to the Web Console.

## 2. Why now

Phase 1 is not acceptable if connectivity or process-up signals can create a
false green state while identity, reconciliation, storage, or privilege is
broken.

## 3. Inputs and decisions

- Conditions use `True`, `False`, or `Unknown` status plus stable type, reason,
  bounded message, observed revision, and transition time.
- Initial types: Edge connected, cert valid, config converged, local DB healthy,
  spool healthy, clock quality, container runtime reachable, and privileged
  helper reachable.
- Heartbeat is 30 seconds and connectivity becomes stale after 90 seconds.
- UI never substitutes mock health for backend truth.

## 4. Dependencies

P1-W1, P1-W7, and P1-W8 allow the health domain to begin. P1-W4, P1-W5, and
P1-W6 are integration dependencies that must close before acceptance.

## 5. Scope

- Edge condition collection, transition rules, persistence, and reporting.
- Control Plane ingestion, projection, aggregate environment status, and API.
- Environment and Edge health views with actionable degraded reasons.
- Failure transition and recovery evidence for helper/runtime/channel/storage.

## 6. Non-goals

- Customer SLA, alert notifications, full coverage verification, incident
  creation, Prometheus/Grafana product UI, or predictive health.

## 7. Allowed paths

Only the health slices, required contracts, tests, and runbook paths listed in
frontmatter. Cross-component changes must remain health-specific.

## 8. Security constraints

Health messages are bounded, enumerated where possible, and contain no private
keys, session secrets, raw database errors, arbitrary HTML, or attacker-supplied
content rendered as markup.

## 9. Implementation requirements

- Condition transitions are deterministic and preserve last transition time.
- Unknown differs from healthy and unhealthy.
- Aggregate status cannot be healthier than a blocking child condition.
- Stale data is explicit; timestamps and clock-quality condition are retained.
- Sequential PR chain is allowed for the contract/domain shell, but final
  acceptance waits for real P1-W4/W5/W6 integration.

## 10. Required tests

- Each condition's healthy, degraded, unknown, stale, and recovery transition.
- Stop/restart helper and container runtime intentionally.
- Disconnect/reconnect, expired/revoked cert, DB failure, and revision drift.
- API/UI hostile-message escaping and no-fake-green browser test.

## 11. Acceptance criteria

- Stopping helper/runtime produces the exact degraded condition.
- Connection, certificate, convergence, and storage truth survive restarts.
- UI shows the backend reason and never a disconnected mock green state.
- Recovery clears only the relevant condition after fresh evidence.

## 12. Evidence required

Condition matrix, transition fixtures, UI screenshots, browser results,
failure-injection logs, and CI links.

## 13. Stop and escalate

Stop for new alert/incident behavior, vendor observability dependency, health
based only on process-up, unbounded/raw error messages, or acceptance without
real integration evidence.

## 14. Deliverables

Health contracts/domain/reporting/UI, deterministic transition tests,
failure-injection evidence, screenshots, and operator runbook.
