# P1-W6 — Build the desired-state reconciler skeleton

## 1. Purpose

Establish revisioned desired/observed state and an idempotent Edge reconciliation
loop that preserves last-known-good behavior across restart and disconnection.

## 2. Why now

Phase 2 decoy deployment depends on a proven configuration-control loop rather
than imperative, non-replayable commands.

## 3. Inputs and decisions

- Declarative revisioned desired-state snapshots.
- At-least-once delivery with idempotent application.
- SQLite WAL stores desired revision, observed revision, conditions, attempts,
  and last-known-good state.
- Initial objects: Edge configuration, zone metadata, and a placeholder decoy
  desired object with no real decoy lifecycle.

## 4. Dependencies

P1-W3 environment/zone identity, P1-W5 channel, and P1-W7 durable Edge shell.

## 5. Scope

- Control Plane desired-state revision storage and publication.
- Edge validation, transactional persistence, apply, observe, and ACK loop.
- Retry metadata, reasoned conditions, and last-known-good selection.
- Deterministic behavior for duplicate, stale, skipped, and invalid revisions.

## 6. Non-goals

- Real decoy deployment, network/firewall mutation, artifact download, active
  discovery, conflict resolution UI, or multi-Edge orchestration.

## 7. Allowed paths

Only the reconciliation, related environment/device adapters, contracts,
SQLite storage, tests, and protocol/runbook paths listed in frontmatter.

## 8. Security constraints

Validate every desired object before mutation. Invalid or unauthorized state
cannot erase last-known-good state or report healthy. No shell command or
privileged operation is introduced by the placeholder object.

## 9. Implementation requirements

- Replaying the same revision is a no-op with stable observed output.
- Revision progression and condition transitions are transactional.
- A failed revision records reason, attempt count, and retry state.
- Restart resumes from persisted state; disconnect causes no destructive change.
- Schema evolution follows the development atomic-update policy.

## 10. Required tests

- Duplicate, stale, out-of-order, skipped, malformed, and unsupported revision.
- Crash before/after commit, restart resume, and rollback-to-last-known-good.
- Disconnect/reconnect and repeated delivery.
- SQLite corruption interaction with the P1-W7 recovery state.

## 11. Acceptance criteria

- Same-revision replay is idempotent.
- Failure reports a precise reason and never pretends to be healthy.
- Last-known-good and retry metadata survive Edge restart.
- Desired and observed revisions converge through the real device channel.

## 12. Evidence required

State-transition fixtures, SQLite rows without secrets, failure-injection logs,
contract evidence, and CI links.

## 13. Stop and escalate

Stop for imperative-only control, hidden privileged action, destructive offline
behavior, real decoy deployment, unbounded retries, or a new datastore/broker.

## 14. Deliverables

Desired-state store, Edge reconciler, versioned contract/schema, deterministic
fixtures, protocol documentation, and recovery runbook.
