# P1-W10 — Implement the audit model

## 1. Purpose

Provide the append-oriented audit contract used by authentication, environment,
enrollment, desired-state, and security-setting mutations.

## 2. Why now

Audit must be present before Phase 1 security-sensitive workflows are built so
it is a transaction boundary, not a best-effort retrofit.

## 3. Inputs and decisions

- First-class append-oriented PostgreSQL audit records.
- Required context: actor, time, action, object, request/correlation identity,
  and redacted before/after references.
- Product API offers no update/delete operation for audit records.
- No separate audit datastore or broker in Phase 1.

## 4. Dependencies

P1-W1 database, transaction, module, and audit-append substrate, aligned to the
canonical downstream package roots by P1-G1.

## 5. Scope

- Audit event schema, typed append API, queries, and paginated read API.
- Actor types for system, authenticated user, and device where applicable.
- Action/object vocabulary for Phase 1 auth, enrollment/revocation,
  environment, desired-state, and security changes.
- Transactional append integration contract for other modules.
- Redaction and bounded before/after serialization.

## 6. Non-goals

- SIEM export, cryptographic ledger/notarization, retention deletion workflow,
  legal archive, audit UI, or full post-MVP action vocabulary.

## 7. Allowed paths

Only the audit module, its API/storage/test/security/runbook paths, and this
specification.

## 8. Security constraints

Never store passwords, session/bootstrap/recovery tokens, TOTP seeds/codes,
device or CA private keys, or unbounded hostile payloads in audit before/after
data. Authorization protects audit reads.

## 9. Implementation requirements

- Append occurs in the same transaction as the audited mutation where safety
  requires atomicity.
- Stable event ID and occurred-at/recorded-at timestamps.
- Before/after uses a versioned redacted JSON structure with size bounds.
- Application roles have no product path to update/delete audit rows.
- Pagination is deterministic and queries are indexed.

## 10. Required tests

- Atomic mutation+audit commit and rollback.
- Attempted product API update/delete rejection.
- Secret-redaction and oversized/hostile before/after payload.
- Pagination ordering, authorization, restart, and concurrent append.

## 11. Acceptance criteria

- Required Phase 1 actions can record actor/time/object/before-after references.
- Audit records cannot be edited or deleted through the product API.
- Failed auth and denied security actions can be recorded safely.
- Restart preserves audit history and deterministic ordering.

## 12. Evidence required

Schema/query review, representative redacted records, API authorization tests,
transaction failure evidence, security review, and CI links.

## 13. Stop and escalate

Stop for mutable audit semantics, plaintext secrets, a second datastore/broker,
retention policy change, or an event vocabulary that expands product scope.

## 14. Deliverables

Audit schema/module/API, transactional integration contract, redaction tests,
security review, and audit support runbook.
