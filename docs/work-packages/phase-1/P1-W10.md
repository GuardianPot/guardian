# P1-W10 — Implement the audit model

## 1. Purpose

Provide the append-oriented audit contract used by authentication, environment,
enrollment, desired-state, and security-setting mutations.

## 2. Why now

Audit must be present before Phase 1 security-sensitive workflows are built so
it is a transaction boundary, not a best-effort retrofit.

## 3. Inputs and decisions

- First-class append-oriented PostgreSQL audit records.
- Required context: actor, time, action, object, request/correlation identity,
  and redacted before/after references.
- Product API offers no update/delete operation for audit records.
- No separate audit datastore or broker in Phase 1.

## 4. Dependencies

P1-W1 database, transaction, module, and audit-append substrate, aligned to the
canonical downstream package roots by P1-G1.

## 4.1 Product Owner implementation contract — 2026-08-24

The Product Owner approved `H1-A` through `H6-A` as one binding implementation
package:

- **H1-A — schema and identity:** expose a durable PostgreSQL 18 `uuidv7()`
  `event_id`; use an internal `bigint` sequence for deterministic pagination;
  store caller-supplied `occurred_at`, database-generated `recorded_at`, actor,
  action, object, required correlation identity, optional request identity, and
  before/after snapshots. Migration `00002` may replace the development audit
  table without compatibility or data migration.
- **H2-A — append-only enforcement:** expose no product update, delete, or
  truncate query/API; reject those operations with a database trigger; document
  a runtime role with only `SELECT` and `INSERT`. This is not a cryptographic
  guarantee against a database administrator or table owner.
- **H3-A — bounded redacted snapshots:** use the
  `guardian.audit.snapshot.v1` envelope with a 16 KiB encoded limit per
  snapshot, maximum depth 6, 256 total nodes, 64 members per object/array,
  64-byte keys, and 512-byte strings. Callers provide safe projections;
  known secret keys are recursively redacted. Invalid, unsupported, or
  oversized snapshots fail the containing transaction rather than truncating.
- **H4-A — closed Phase 1 vocabulary:** enforce matching Go constants and
  database checks for bootstrap-token creation; bootstrap and login success or
  failure; logout; password change; MFA enrollment; recovery-code use; session
  revocation; security-setting change; enrollment-token creation or revocation;
  enrollment success or failure; certificate issue or rotation; device disable
  or revocation; environment create or update; zone create, update, or removal;
  desired-state revision publication; and denied security actions. Object types
  are closed to the corresponding Phase 1 resources. Incident, AI, update,
  decoy, and suppression/allowlist vocabulary remains for later owner-reviewed
  packages.
- **H5-A — read API and authorization:** provide `GET /v1/audit/events` with
  newest-first keyset pagination, default limit 50, maximum 200, and a versioned
  Base64URL cursor carrying a first-page sequence anchor. Allow exact action and
  correlation filters plus paired object-type/object-ID filters. Define the
  `__Host-guardian_session` operation-level cookie contract; until P1-W2 wires
  authentication, default-deny with `401` before any database query. Mutation
  methods have no operation and return `405`.
- **H6-A — atomic module boundary:** the audit module owns events, records,
  validation, redaction, and `Appender`/`Reader` contracts; storage implements
  them. Storage adapters append the mutation and its audit event in the same
  `pgx` transaction. Domain and API packages do not import storage, `pgx`, or
  SQL implementations.

## 5. Scope

- Audit event schema, typed append API, queries, and paginated read API.
- Actor types for system, authenticated user, and device where applicable.
- Action/object vocabulary for Phase 1 auth, enrollment/revocation,
  environment, desired-state, and security changes.
- Transactional append integration contract for other modules.
- Redaction and bounded before/after serialization.

## 6. Non-goals

- SIEM export, cryptographic ledger/notarization, retention deletion workflow,
  legal archive, audit UI, or full post-MVP action vocabulary.

## 7. Allowed paths

Only the audit module, its API/storage/test/security/runbook paths, and this
specification.

## 8. Security constraints

Never store passwords or password hashes; session, bootstrap, enrollment,
recovery, access, or refresh tokens; TOTP seeds/codes; device or CA private
keys; authorization/cookie values; or unbounded hostile payloads in audit
before/after data. Authorization protects audit reads.

## 9. Implementation requirements

- Append occurs in the same transaction as the audited mutation where safety
  requires atomicity.
- Stable event ID and occurred-at/recorded-at timestamps.
- Before/after uses a versioned redacted JSON structure with size bounds.
- Application roles have no product path to update/delete audit rows.
- Pagination is deterministic and queries are indexed.

## 10. Required tests

- Atomic mutation+audit commit and rollback.
- Attempted product API update/delete rejection.
- Secret-redaction and oversized/hostile before/after payload.
- Pagination ordering, authorization, restart, and concurrent append.

## 11. Acceptance criteria

- Required Phase 1 actions can record actor/time/object/before-after references.
- Audit records cannot be edited or deleted through the product API.
- Failed auth and denied security actions can be recorded safely.
- Restart preserves audit history and deterministic ordering.

## 12. Evidence required

Schema/query review, representative redacted records, API authorization tests,
transaction failure evidence, security review, and CI links.

## 13. Stop and escalate

Stop for mutable audit semantics, plaintext secrets, a second datastore/broker,
retention policy change, or an event vocabulary that expands product scope.

## 14. Deliverables

Audit schema/module/API, transactional integration contract, redaction tests,
security review, and audit support runbook.

## 15. Implementation evidence — 2026-08-24

The implementation candidate on `agent/P1-W10-audit-model` provides the
approved `H1-A` through `H6-A` contract within this package's allowed paths.

- PostgreSQL 18 integration exercises atomic commit and rollback, runtime-role
  least privilege, append-only trigger enforcement, null and malformed-row
  bypass attempts, exact snapshot byte boundaries, first-page anchor races,
  restart persistence, filtering, and concurrent append pagination.
- Audit model, snapshot, cursor, API authorization, method rejection, and
  vocabulary tests pass under `go test`; `go vet`, `mod verify`, generated-code
  drift, OpenAPI validation, vulnerability scanning, and license checks pass.
- The storage integration suite passes under Linux CGO race instrumentation.
  An independent implementation/security review reported no blocker, major,
  or minor finding.
- The audit development runbook records the exact runtime grants, verification
  queries, append/read protocol, local fixture workflow, and recovery boundary.
  The security review records threat assumptions, controls, residual risks, and
  the P1-W2 authentication dependency.

The repository-wide Ubuntu `task validate` result and its immutable GitHub
Actions link remain required before the pull request may enter security review.
Windows-native validation is supporting evidence only: the repository policy
parser assumes LF input and the Edge Agent integration types are Linux-only.
The staged-index LF policy checks and pinned Linux package tests pass; these
platform constraints do not waive the required Ubuntu CI gate.

Known limitations remain explicit: this is not DBA/owner tamper resistance,
cryptographic notarization, SIEM export, legal retention, or a complete
post-MVP vocabulary. Snapshot redaction is defense in depth; callers remain
responsible for providing safe projections. Audit reads remain default-denied
until P1-W2 supplies the approved cookie-session authorizer.
