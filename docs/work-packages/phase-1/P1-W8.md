# P1-W8 — Implement the privileged helper

## 1. Purpose

Provide a minimal root-owned helper for the exact host operations that the
unprivileged Edge daemon cannot perform.

## 2. Why now

Phase 1 health and Phase 2 runtime/networking require a tested privilege
boundary before attacker-facing components are introduced.

## 3. Inputs and decisions

- Protobuf/gRPC over a local Unix domain socket.
- Linux peer credentials validated with `SO_PEERCRED`-class primitives.
- Typed allowlisted methods only; no shell strings or arbitrary paths.
- Initial methods cover address, nftables policy, container lifecycle hook, and
  network namespace operations.
- Change proposal 0002 corrects the roadmap reference: P1-W8 is bound to the
  approved `SEC-04` boundary and Phase 1 privileged-helper security tests.
  `AC-SEC-004` remains in Phase 2 primary validation and Phase 5 final
  regression for unsigned/tampered OCI artifact rejection.
- Product Owner decision F2-A corrects the execution scope so generated
  Protobuf/gRPC code, pinned Edge dependencies, validation wiring, and the
  existing Edge component integration can change atomically. It does not alter
  product scope, privileges, the trust boundary, or acceptance criteria.

## 4. Dependencies

P1-W7 defines the unprivileged daemon lifecycle and client interface.

## 5. Scope

- Root-owned helper process and restrictive systemd/socket profile.
- Versioned local RPC contract and unprivileged client.
- Strict request validation, operation allowlists, and audit records.
- Minimal Linux capability/seccomp hardening where supported.
- Initial operation adapters may return explicit unsupported status until the
  approved Phase 2 implementation fills their full runtime behavior.

## 6. Non-goals

- Arbitrary command execution, general filesystem API, decoy-facing socket,
  completed Phase 2 network/container lifecycle, or non-Linux support.

## 7. Allowed paths

Only the helper/client, local contract, Edge component integration, pinned
module manifests, generation/validation wiring, service profile, security
tests/review, and runbook paths listed in frontmatter.

## 8. Security constraints

- Socket is local, root-owned, and accessible only to the dedicated Edge
  identity/group.
- Verify peer PID/UID/GID before dispatch and reject unexpected peers.
- Validate interface names, addresses, namespaces, handles, and policy objects
  against explicit allowlists and bounds.
- Decoy processes cannot access the socket.

## 9. Implementation requirements

- Generated typed messages and explicit method-level authorization.
- No command shell, user-provided executable, arbitrary path, or raw nft script.
- Every accepted/rejected operation creates a redacted audit event.
- Cancellation, timeout, concurrency, and idempotency semantics are explicit.
- Helper failure leaves the Edge daemon alive but precisely degraded.

## 10. Required tests

- Authorized peer and wrong UID/GID/PID/socket permissions.
- Path traversal, malformed message, oversized message, unknown method, and
  command-injection payload.
- Allowlist boundary and idempotent retry tests.
- Helper stop/restart and no-decoy-access network-lab test.
- Capability/seccomp profile smoke where the runner supports it.

## 11. Acceptance criteria

- The approved `SEC-04` typed-helper boundary and Phase 1 privileged-helper
  security tests pass.
- No arbitrary command/path API exists.
- Unauthorized peers and malformed requests fail closed and are audited.
- Helper loss produces a precise degraded condition without daemon crash.

## 12. Evidence required

Socket/service ownership evidence, RPC contract diff, abuse-test results,
capability profile, independent security review, and CI/lab links.

## 13. Stop and escalate

Stop for a new privileged operation, broad root daemon, shell execution, raw
runtime socket delegation, missing peer validation, or an allowlist that cannot
be enforced safely.

## 14. Deliverables

Helper and client binaries, versioned local RPC, service/socket profile,
security regression suite, audit evidence, and support runbook.

## 15. Implementation evidence

Local candidate evidence recorded on 2026-08-23:

- `task validate`: pass, including repository policy, generated-code
  freshness, Buf/OpenAPI contracts, Go vet/unit/race tests, web checks,
  Control Plane PostgreSQL integration, Edge restart/WAL fixtures, and the
  hardened Control Plane container smoke.
- `task privileged:security`: pass, including the isolated root-owned socket
  lab, authorized UID/GID, wrong UID/GID, decoy filesystem denial, abuse
  cases, and systemd profile verification.
- `systemd-analyze security --offline=yes`: `1.1 OK` for
  `guardian-edge-privd.service`.
- `govulncheck v1.7.0 -show verbose ./...`: no vulnerabilities found across
  the Edge module and Go 1.27.0 standard library.
- `go-licenses v2.0.1 check ./...`: pass; non-Go assembly warnings were
  resolved against the module-root BSD/MIT license files.
- Two `CGO_ENABLED=0`, `-trimpath`, empty-build-ID helper builds were
  byte-identical at SHA-256
  `5ad5e492e91fa4097a847754ab59dcdda2aed52fdc777f03afcd8cc43eed8b05`.

Security impact: the Edge daemon remains unprivileged and receives only four
typed, allowlisted operations over the fixed root-owned Unix socket.
Authentication happens before protobuf dispatch, audit data is metadata-only,
and P1 production capabilities remain empty.

Known limitations: all four host-mutating adapters intentionally report
`phase-2-adapter-not-implemented`; the idempotency cache is process-local; and
installed-host service execution is deferred to packaging/integration while
the unit is verified offline and the root/socket behavior is exercised in the
isolated container. PR-level owner and independent security review remain
required before acceptance.
