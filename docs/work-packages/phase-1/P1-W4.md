# P1-W4 — Implement Edge enrollment and revocation

## 1. Purpose

Turn the Phase 0 disposable PKI proof into the product-owned, persistent Edge
enrollment, certificate rotation, and revocation lifecycle.

## 2. Why now

The device channel cannot establish production-shaped identity or authorization
until Edge records and one-time enrollment are durable and auditable.

## 3. Inputs and decisions

- Product-specific X.509 device CA using standard Go cryptography.
- Edge generates and retains its own private key.
- One-time enrollment tokens expire after 15 minutes and are hashed at rest.
- Device certificates are valid for 30 days and rotate with jitter during the
  final 10 days.
- Central CA material uses the SecretStore boundary; no plaintext CA key in
  PostgreSQL or logs.

## 4. Dependencies

P1-W1 persistence, P1-W7 Edge identity/storage shell, P1-W10 audit, and the
accepted P0-W9 PKI evidence inherited through the Phase 0 gate.

## 5. Scope

- Authenticated enrollment-token create/list/revoke API.
- Edge key generation, CSR construction, and enrollment exchange.
- Certificate issuance, persistence metadata, rotation, and expiry state.
- Device record, connection eligibility, disable/revoke, and re-enrollment
  boundary.
- Audit for token, issuance, rotation, disable, and revocation actions.

## 6. Non-goals

- TPM requirement, enterprise PKI, SPIFFE/SPIRE, production KMS vendor,
  multi-device fleet rollout, or Web Console wizard.

## 7. Allowed paths

Only the PKI/device, Edge enrollment, contract, test, security, and runbook
paths listed in frontmatter.

## 8. Security constraints

- Token and certificate use is bound to the intended environment/device flow.
- Token consume is atomic and replay-safe.
- Edge private keys never cross the device API or enter logs.
- Revoked/disabled identities cannot establish a new management session.
- Test fixtures use disposable CA material only.

## 9. Implementation requirements

- Use cryptographically random token material with only a hash persisted.
- Issue certificates only after CSR validation and explicit token consume.
- Persist serial, validity, fingerprint, state, and rotation metadata.
- Provide a protected local SecretStore development backend using a mounted
  master-key file; keep hosted KMS behind the stable interface and out of scope.
- Update all development protocol consumers atomically; add no compatibility
  layer for obsolete development contracts.

## 10. Required tests

- Fresh enrollment, expired/invalid/revoked/used token, and concurrent replay.
- CSR/key mismatch, malformed CSR, and unsupported key/signature input.
- Rotation before/inside the window and service restart during rotation.
- Device disable/revoke and rejected new mTLS session.
- Secret/log scan and filesystem permission assertions.

## 11. Acceptance criteria

AC-ON-001, AC-ON-002, AC-SEC-005, and AC-SEC-006 pass with durable audit
evidence and no Edge private-key disclosure.

## 12. Evidence required

Enrollment/rotation/revocation test logs, redacted certificate metadata, threat
review, SecretStore boundary evidence, and CI links.

## 13. Stop and escalate

Stop for custom cryptography, plaintext CA/device private keys, reusable tokens,
external PKI/KMS dependency, weaker revocation, or expanded device identity
semantics.

## 14. Deliverables

Enrollment and device modules, Edge identity client, API/contracts,
migrations/tests, security review, and operator runbook.
