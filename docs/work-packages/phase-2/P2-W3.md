# P2-W3 — containerd production runtime manager

## 1. Purpose

Run a decoy as a container that holds nothing of the host, and converge the
host's containers on what the Control Plane asked for.

## 2. Where the runtime detail comes from

`ReconcileContainer` carries a workload id and a desired state, and nothing
else. `P2-W15`, `P2-W4`, and the pack index each say that no API field may ever
supply an image, command, mount, or capability. The Edge Agent can ask for a
workload by name; it cannot describe one.

So the description lives where the Edge cannot write: a root-owned **workload
definition** at `/etc/guardian-edge/workloads/<workload-id>.json`, installed
beside the helper. A container can exist only if root installed a definition
*and* root allowlisted its id with `--allow-workload`. An attacker in full
control of the Edge Agent can choose which installed workload runs and whether
it runs. They cannot invent one, name an image, add a capability, or mount a
path, because there is no field in which to say any of those things.

The definition is validated before anything reads it as meaning: schema version
first, unknown fields refused, the image pinned by `sha256` digest (a tag can be
moved after approval), capabilities from the manifest's closed set of one, a
non-root uid and gid, and resource limits required. The file is read with
`Lstat` and the opened descriptor is compared with what was checked, so a
symlink cannot redirect a root process to another file.

## 3. What a decoy is granted

`BuildContainerSpec` writes a deliberately small OCI spec that starts from
nothing and adds only what a decoy needs:

- A read-only root filesystem; writable areas are bounded tmpfs. The telemetry
  directory `/var/log/guardian` belongs to the decoy's own uid and is `noexec`,
  so a pack can write what its adapter reads but cannot run what it wrote.
- Every namespace new — pid, ipc, uts, mount, network, cgroup — and none with a
  path, so nothing is joined.
- Capability sets built from the grant: exactly `CAP_NET_BIND_SERVICE` when
  declared, empty otherwise, with `noNewPrivileges`.
- The workload's uid, never the image's: an image configured to run as root
  does not get to.
- Memory (no swap beyond it), CPU quota, pids, and a deny-all device cgroup.
- Masked and read-only `/proc` and `/sys` paths that would describe the host.
- The default seccomp allowlist Docker and containerd ship, used as published
  (section 4).
- No mount with a host source. The only sources are kernel filesystems, so
  `AC-SEC-001` (no device key path) and `AC-SEC-002` (no runtime socket) hold
  because there is no code that could emit a bind mount.

The image contributes only its program: arguments, environment, and working
directory, bounded and validated. That cannot grant anything — it runs inside
the container, as Guardian's uid, with Guardian's capabilities.

## 4. How it is run

**The runtime.** `ReconcileContainer` drives containerd 2.x through its
generated API (`containerd/api`, already a dependency) rather than its client
library. The image is fetched by digest through containerd's Transfer service,
which verifies content against that digest; the helper then walks index →
manifest → config itself, checking every blob's hash, to learn the program and
the root filesystem's chain id. Every request is scoped to the containerd
namespace `guardian-decoy`, so the helper cannot see or touch any container it
did not create.

**The rules.** Stopping and removing act on the workload id alone and never
depend on the definition, so an uninstalled definition can still be removed. A
decoy never starts unless the default-deny egress policy is installed for the
configured ranges right now — the `P2-W2` ordering, enforced where decoys are
started. A dead task under a desired running state is restarted on the next
pass; that is the restart policy, with the reconciler's cadence as the backoff.
A container whose spec digest no longer matches the installed definition is
replaced. A failed start removes the task and container it left.

**Seccomp.** `seccompprofile/default.json` is `github.com/moby/profiles/seccomp`
v0.2.3, the file Docker Engine 29.8.0 vendors, unmodified and pinned by hash,
under its Apache-2.0 licence. Guardian maintains only the translation from
Docker's conditional format to OCI, resolving capability, architecture, and
kernel conditions against the decoy's grant and the host. For a decoy granted
`NET_BIND_SERVICE` it denies by default and keeps mount, namespace, module,
`bpf`, keyring, and `io_uring` syscalls out. Unlike the blocklist it replaced,
upstream allows `ptrace` on kernels from 4.8; a decoy can trace its own
processes in its own pid namespace and nothing else.

**Privilege.** No service directive changed. containerd does the privileged
work, and the helper reaches it over the socket the runtime probe already used.
That socket is a root-equivalent API, so what actually contains a decoy is that
the helper can only send containerd the output of `BuildContainerSpec`; the
security review records this plainly. `ReconcileContainer` alone gets a
three-minute bound, since a first pass may fetch an image; every other
privileged call keeps five seconds.

**Evidence.** `task privileged:containerd` runs a pinned containerd 2.3.5 and
runc 1.5.1 in a throwaway privileged container and pulls busybox by its index
digest from a real registry. A probe runs _as the decoy_ and exits with the code
of the first property that fails: the runtime socket and directory are
invisible, it is uid 10001, the root is read-only, its effective and bounding
capabilities are exactly `NET_BIND_SERVICE`, `no_new_privs` and a seccomp
filter are in force, its telemetry directory is writable and not executable, it
sees no Guardian path, only `lo`, and its own hostname. The cgroup limits are
read from the host side. The lab then crashes a running decoy and watches it
restart with a new pid, stops one and keeps its container, edits a definition
and sees the container rebuilt with the new memory limit, makes a start fail and
finds nothing left behind, and confirms the decoy does not exist when looked up
from containerd's default namespace.

The lab corrected two things the unit tests could not: the root snapshot must
be writable to runc so it can create mount points an image does not ship (the
decoy still sees a read-only root), and the telemetry tmpfs was root-owned, so a
non-root decoy could not have written its own events.

## 5. Status

**Implemented:** workload definitions, the spec, digest-pinned image
acquisition, the container and task lifecycle, reconciliation with restart and
cleanup, the egress ordering, and the upstream seccomp allowlist.

**Not implemented: network attachment.** A running decoy today has its own
network namespace with only `lo`. It is isolated and unreachable, which the
decoy observed state can already express truthfully: runtime healthy, port not
responding. See section 7.

## 6. Ordering carried in from P2-W2

nftables state does not survive a reboot, so `ReconcileContainer` refuses a
running state with `egress-policy-not-applied` until the policy for exactly the
configured ranges is installed. The check reads the kernel, not a flag the
helper remembers.

## 7. Owner decisions

1. **Network attachment — reopened on evidence.** The accepted direction was
   that the runtime creates each decoy's namespace and the helper attaches it
   with the `CAP_NET_ADMIN` it already holds. Tested on a real kernel, half of
   that holds: moving a veth into a decoy's namespace needs only
   `CAP_NET_ADMIN`. Configuring anything _inside_ that namespace does not:
   entering it needs `CAP_SYS_PTRACE` to open another process's namespace and
   `CAP_SYS_ADMIN` to join it. That is more privilege than the option it was
   meant to avoid.

   It also meets `ADR 0016`. A decoy address bound on the host's edge interface
   is terminated by the host, so reaching a container needs either DNAT — after
   which the container's source address is no longer in the decoy ranges
   `P2-W2`'s policy is keyed on — or the address living inside the container,
   with the host proxying ARP and routing a `/32` to the veth, which is not what
   the ADR says.

   The design that keeps both the helper's privilege and the egress policy's
   scope intact is a Guardian **network-holder container** per decoy: it owns
   the namespace, holds `CAP_NET_ADMIN` inside it only, configures the address
   and route from inside with a small Guardian binary, and listens on nothing;
   the helper moves the veth in (proven to work), the host routes the `/32` to
   it and proxies ARP, and the decoy joins the holder's namespace. It costs a
   Guardian-built image and an amendment to `ADR 0016`, and it needs its own lab
   before it can be recommended with confidence.

2. **Seccomp.** Done: the upstream allowlist, as recommended.
3. **The workload file format.** Kept in Go and documented in the runbook, as
   recommended.

## 8. Acceptance criteria

1. A decoy container has no host mount, no joined namespace, no capability
   beyond its grant, and no root user. **Met, and asserted from inside a running
   decoy.**
2. A workload that is not installed and allowlisted cannot run. **Met.**
3. Create, start, stop, and remove are idempotent, and a failed create cleans up
   after itself. **Met, against a real containerd.**
4. A crashed decoy is restarted under the declared policy. **Met: restarted on
   the next pass, with a new pid.**
5. A running decoy cannot reach the runtime socket, proven from inside a
   container. **Met.**
6. `task check` passes.

A decoy that answers on the network is not among them, and does not exist yet:
that is decision 1.
