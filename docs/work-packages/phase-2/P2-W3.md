# P2-W3 — containerd production runtime manager

## 1. Purpose

Run a decoy as a container that holds nothing of the host, and converge the
host's containers on what the Control Plane asked for.

## 2. Where the runtime detail comes from

`ReconcileContainer` carries a workload id and a desired state, and nothing
else. `P2-W15`, `P2-W4`, and the pack index each say that no API field may ever
supply an image, command, mount, or capability. The Edge Agent can ask for a
workload by name; it cannot describe one.

So the description lives where the Edge cannot write: a root-owned **workload
definition** at `/etc/guardian-edge/workloads/<workload-id>.json`, installed
beside the helper. A container can exist only if root installed a definition
*and* root allowlisted its id with `--allow-workload`. An attacker in full
control of the Edge Agent can choose which installed workload runs and whether
it runs. They cannot invent one, name an image, add a capability, or mount a
path, because there is no field in which to say any of those things.

The definition is validated before anything reads it as meaning: schema version
first, unknown fields refused, the image pinned by `sha256` digest (a tag can be
moved after approval), capabilities from the manifest's closed set of one, a
non-root uid and gid, and resource limits required. The file is read with
`Lstat` and the opened descriptor is compared with what was checked, so a
symlink cannot redirect a root process to another file.

## 3. What a decoy is granted

`BuildContainerSpec` writes a deliberately small OCI spec that starts from
nothing and adds only what a decoy needs:

- A read-only root filesystem; writable areas are bounded tmpfs, `noexec`
  where a decoy writes.
- Every namespace new — pid, ipc, uts, mount, network, cgroup — and none with a
  path, so nothing is joined.
- Capability sets built from the grant: exactly `CAP_NET_BIND_SERVICE` when
  declared, empty otherwise, with `noNewPrivileges`.
- The workload's uid, never the image's: an image configured to run as root
  does not get to.
- Memory (no swap beyond it), CPU quota, pids, and a deny-all device cgroup.
- Masked and read-only `/proc` and `/sys` paths that would describe the host.
- No mount with a host source. The only sources are kernel filesystems, so
  `AC-SEC-001` (no device key path) and `AC-SEC-002` (no runtime socket) hold
  because there is no code that could emit a bind mount, and the tests check
  the serialised spec rather than the struct.

The image contributes only its program: arguments, environment, and working
directory, bounded and validated. That cannot grant anything — it runs inside
the container, as Guardian's uid, with Guardian's capabilities.

## 4. The privilege question is not containerd

containerd is a root daemon that does the privileged work of creating a
container. The helper only calls its API over the socket it already probes, so
the container half of this package should need **no new capability**. The unit
already lists `ReadOnlyPaths=-/run/containerd/containerd.sock`, and a read-only
mount does not prevent `connect()` on a socket.

The capability question is `EnsureNetworkNamespace`. Creating a persistent
network namespace needs `CAP_SYS_ADMIN`, which is close to unrestricted root and
costs more than the roughly 0.2 of headroom left under the security gate's
exposure ceiling. Whether the routed placement needs a Guardian-created
namespace at all, or can attach a runtime-created one, is the topology decision
in section 7.

## 5. Status

**Implemented:** the workload definition, its loader, and the OCI spec builder,
with tests asserting every prohibition in section 3.

**Not yet implemented:**

1. Image acquisition by digest. containerd 2.x's Transfer API performs the pull
   server-side, and its types ship in `containerd/api`, which is already a
   dependency, so this needs no new module.
2. Snapshot, container, and task lifecycle: create, start, stop, remove, and
   cleanup of partial resources on failure.
3. Reconciliation and restart policy behind `ReconcileContainer`, which still
   reports `phase-2-adapter-not-implemented`.
4. Network attachment, which waits on section 7.
5. A lab against a real containerd. Debian bookworm's packaged containerd
   predates the Transfer API, so the lab needs pinned containerd 2.x binaries
   in a privileged test container.

## 6. Ordering carried in from P2-W2

nftables state does not survive a reboot. The lifecycle must not start a decoy
before the egress policy has been applied on the current boot. This package is
where that ordering has to be enforced, because it is the one that starts
decoys.

## 7. Owner decisions

1. **Network attachment and `CAP_SYS_ADMIN`.** Either the helper creates and
   owns decoy network namespaces (`EnsureNetworkNamespace`, needs
   `CAP_SYS_ADMIN` and a profile change past the current ceiling), or the runtime
   creates them and the helper attaches a veth using the `CAP_NET_ADMIN` it
   already has. The second keeps the privilege where it is. It needs a concrete
   design and a lab before it can be recommended with confidence.
2. **Seccomp.** The spec carries a blocklist of escalation syscalls. A
   default-deny allowlist of the kind Docker and containerd ship is stronger,
   and doing it properly means adopting a maintained profile rather than
   writing several hundred lines of policy by hand. `P2-W5` (Cowrie, medium
   interaction) should not ship on the blocklist alone.
3. **The workload file format.** Defined in Go and documented in the runbook,
   not in `schemas/`, because it is read by one helper on one host and is not a
   wire contract. Publishing it beside the decoy manifest schema is a one-file
   change if preferred.

## 8. Acceptance criteria

1. A decoy container has no host mount, no joined namespace, no capability
   beyond its grant, and no root user. **Met by construction and test.**
2. A workload that is not installed and allowlisted cannot run. **Met for
   installation; allowlisting is enforced by the existing RPC validation.**
3. Create, start, stop, and remove are idempotent, and a failed create cleans up
   after itself. **Not yet.**
4. A crashed decoy is restarted under the declared policy. **Not yet.**
5. A running decoy cannot reach the runtime socket, proven from inside a
   container. **Not yet** — criterion 1 is the structural half.
6. `task check` passes.
