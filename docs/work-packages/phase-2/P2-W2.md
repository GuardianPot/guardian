# P2-W2 — nftables egress policy

## 1. Purpose

Make a decoy unable to start an outbound connection, so that running
attacker-facing software is a containable decision.

## 2. Why this comes before every pack

`Cowrie` is medium-interaction software: it runs code an attacker typed. Nothing
in `P2-W5` through `P2-W8` may be deployed until a decoy that is fully
compromised still cannot reach production or the internet. That is the whole of
`AC-SEC-003`, and it is why the agreed order puts this package ahead of all four
packs.

## 3. The three questions this package had to answer

**Where do the rules live?** `ADR 0016` had already decided: default-deny
`forward`/`output` policy. Those are host-namespace chains, which turned out to
matter more than it looks. Applying rules *inside* a decoy's own network
namespace would require `setns`, which requires `CAP_SYS_ADMIN` — a capability
close to unrestricted root, and one the helper's service profile has no room
for. Host-side enforcement needs only the `CAP_NET_ADMIN` that `P2-W1` already
granted, so **this package widened no privilege at all**. It is also the
stronger placement: rules inside a namespace can be flushed by anything that
gains `CAP_NET_ADMIN` in that namespace, and rules in the host cannot.

**What does the policy match on?** Not an interface and not a namespace, but the
decoy address ranges the helper was started with. Those are root-controlled
startup arguments, never RPC input, and they are the *same compiled set* that
gates `EnsureAddress`. So the set of addresses Guardian can place and the set it
denies egress for cannot drift apart, and the policy needs no knowledge of how
`P2-W3` will name a decoy's namespace or veth — a coupling that, had it been
built, would have failed silently the day those names changed.

**What is allowed through?** Replies, and nothing else. Every MVP pack's manifest
declares `egress.allow: []`, and the schema says why: "a decoy that needs to
reach something is a decoy that can be used to reach something". Telemetry does
not need an exception either — `P2-W11` reads decoy output from files, so the
evidence path is not a network path. The single profile the contract defines is
therefore the complete policy.

## 4. The rules, and why they are shaped this way

```
table ip guardian_decoy {
    chain guardian_egress {
        ct state established,related accept
        drop
    }
    chain guardian_forward { type filter hook forward priority 0; policy accept;
        ip saddr <decoy range> jump guardian_egress
    }
    chain guardian_output  { type filter hook output  priority 0; policy accept;
        ip saddr <decoy range> jump guardian_egress
    }
}
```

**Base chains accept, rules deny.** A chain policy applies to every packet
reaching that hook, so a `drop` policy in a Guardian table would drop the host's
own forwarded traffic. Denial belongs in the rules, scoped to decoy sources. A
drop in any table still wins, so a deny-shaped policy composes safely with
whatever firewall the customer already runs.

**Both hooks.** `forward` is a decoy in its own namespace. `output` is anything
the host itself sends from a decoy address. `ADR 0016` names both.

**Established replies are accepted, not new connections.** An attacker reaching
a decoy is inbound; the decoy's answer is the reply direction of that flow. A
decoy opening its own connection is `new`, and falls through to the drop.

**Every rule carries a marker.** The policy version, a digest of the ranges it
was built from, and its position. That is what distinguishes "already applied"
from "somebody flushed the table" and from "the configured ranges changed" —
without it, a control that had been removed would keep reporting success.

**The transaction is atomic, and the result is read back.** The table is
created, deleted, and recreated in one nftables batch, so there is no moment at
which it exists without its rules. Then the ruleset is read back from the kernel
before the helper reports it applied, because a transaction the kernel
acknowledged and a policy that is present are two different facts.

**An empty policy is never "applied".** A helper with no decoy ranges reports
the capability `unsupported` with `no-decoy-ranges-configured` rather than
installing rules that match nothing. Telling an operator their decoys are
contained when nothing is containing them is the worst available failure.

## 5. Evidence

`AC-SEC-003` is a claim about a packet, not about a ruleset — and a ruleset test
would pass just as happily on a hand-encoded policy that matches nothing, which
is exactly how this kind of code fails.

`task privileged:netlink` therefore sends packets, in a controlled experiment:
same destination, same route, same socket type, only the source address differs.

- Before the policy, both a decoy source and the host's own source send fine.
- After it, the decoy source is refused by the kernel with `EPERM`.
- The host's own source still sends. A containment control that also broke the
  host would be withdrawn the first time it ran.
- Deleting the table behind the adapter's back restores egress, is detected as
  unconverged, and the next apply denies again.

## 6. Non-goals

- **No per-decoy policy.** The contract defines one profile and every manifest
  declares the same empty allow list. A second profile is a schema change with a
  review attached, which is how `P2-W4` intended it.
- **No namespace or container work.** `EnsureNetworkNamespace` and
  `ReconcileContainer` remain unimplemented; they are `P2-W3`.
- **No inbound filtering.** A decoy exists to be reached. Only what it can
  originate is restricted.

## 7. What this does not cover

**Reboot.** nftables state is kernel state and does not survive one. The
"persists/reconciles" acceptance is met by reconciliation rather than by
persistence: the policy is reinstalled on the next pass. The consequence is an
ordering requirement on `P2-W3` — a decoy must not be started before the policy
has been applied — and nothing in this package can enforce that, because nothing
in this package starts a decoy.

**Nothing calls it yet.** As with `P2-W1`, the adapter is complete and idle: the
Edge has no reconcile loop asking for the policy. The capability is reachable
over the helper's RPC and unexercised in production.

**A misconfigured allowlist.** A range containing production addresses would
have its egress denied. This is the same configuration error `P2-W1`'s review
names, with the same answer: `--allow-address-range` takes decoy ranges only.

## 8. Acceptance criteria

1. A decoy cannot open an outbound connection; proven by a refused packet.
2. The host's own traffic is unaffected by the policy.
3. Applying the policy twice reports no change.
4. A flushed or removed policy is detected and reinstalled.
5. A policy built from different ranges is not mistaken for the installed one.
6. A helper with nothing to protect reports `unsupported`, never `applied`.
7. `task check` passes.

All seven are met. The privileged surface is unchanged from `P2-W1`:
`systemd-analyze security` remains at 1.8.
